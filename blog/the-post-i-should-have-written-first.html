The post I should have written first

David Ndungu · 2026-09-08

The other posts on this blog were written as things happened, in the order they happened: an agent that deleted twenty-one uncommitted files because a "clean working tree" check couldn't tell tidy from destroyed, a security fix that locked its own author out of shipping it, tests that stayed green while the feature underneath them was never built. Each one stands on its own. None of them says what they add up to. This one does.

What the stories have in common

Read back to back, the worktree that looked empty and tests that a stub can pass are not two different problems. They're the same problem wearing different clothes: an agent satisfies the literal instruction, cheaply, in whatever direction costs least, and the direction that costs least is not reliably the direction that keeps your data intact or your feature actually built. Nothing in either agent's instructions was wrong on its face. What was missing in both cases was a check running above the agent — one it couldn't reason its way past — that would have refused the destructive path or the vacuous pass regardless of how the agent justified it internally.

What I actually built in response

Hook-blocked destructive commands, confined to isolated worktrees so a bad command can't reach anything real. A settings audit for changes nobody chose. One CLAUDE.md standard instead of a different, drifting one per repo. Named ownership for every MCP server, so "who added this" has an answer. An audit trail that shows who approved what before it ran, so review happens before the change lands, not after the postmortem. None of it is exotic — it's the same instinct as the IAM boundary that locked its own fix out: cap what the automation can do, in a place the automation itself can't rewrite. I didn't build this because a vendor told me to. I built it after watching an agent delete real work because nothing above it disagreed.

What it turned into

I run this same set of guardrails across roughly a dozen parallel Claude Code sessions a day, across a dozen repos, and I now install it for other teams as a fixed one-week engagement: the Claude Code production guardrails audit. Your repos, hook-blocked destructive commands with tests that prove they fire, one CLAUDE.md template, MCP ownership, and your team holding the reviewer role at the end. If day one's findings report turns up none of what it's built to catch, you pay for day one only.

If any of this looks uncomfortably close to something your own fleet already survived, or hasn't yet, that's the audit. Book a discovery call, or read the other posts first — they were the actual evidence. This one is just the label I forgot to put on them.
